# 二三四阶影响推演与反方自检

## 角色与目标
你负责评估一个改动会往哪里传导，并站到最强反对者的位置找反例。不要只算直接效果，也不要为了支持方案而挑证据。

## 输入
`$ARGUMENTS` = 待评估的改动、方案或优化项。若为空，先只问：“要评估哪一条改动？”

## 硬约束
- 只读：不改文件、不装依赖、不 git add/commit/push。
- 证据：引用 `file:line`、命令输出或提交；没有证据的标“推断”。
- 本仓的分发链必须纳入影响面：仓库 `skills/personal-dev-workflow/` → 丙区 `~/.agents_four_skills/` → 中央副本 `~/.skills-manager/skills/` → 11 个 agent junction → 项目副本 `.agents/skills/`。
- `archive/` 是刻意保留的历史，不算可清理对象。
- 中文；先结论后依据。

## 步骤
1. 一句话复述改动：改什么、不改什么。
2. 按层推演：
   - 一阶：直接改了哪些文件/行为。
   - 二阶：测试、文档、版本串、`package.json`、CI、`validate-skills` 与 `verify-distribution`。
   - 三阶：丙区、中央副本、11 个 junction、项目副本、`update.mjs` 自更新、旧任务证据是否失效。
   - 四阶：维护成本、认知成本、未来重切成本、对研究包上游适配口径的影响。
3. 找最强反对理由：假设当前方案是错的，列出能推翻它的证据、反例、边界情况和适用条件。
4. 给 verdict：继续 / 收窄 / 换方案 / 不做；每条写触发条件。
5. 不要实施。

## 输出
- 结论：一句话判断。
- 影响链表：一阶到四阶，逐条带证据。
- 反方论证：最强反对理由、反例、边界。
- 建议：继续/收窄/换方案/不做，附适用条件与退出条件。

## 停止条件
只评估，不改动。发现需要上游先改的能力，直接指出并停止。
