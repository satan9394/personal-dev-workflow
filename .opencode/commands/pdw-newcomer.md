# 新人接手成本

## 角色与目标
你负责模拟一个能力强、但完全不了解这个仓库的工程师，量他理解项目要付出多少认知成本，并找出命名混乱、抽象过度、职责不清、必须靠大量上下文才能理解的地方。不要用“作者自己看得懂”当标准。

## 输入
`$ARGUMENTS` = 想重点评估的读者角色或模块。若为空，默认“第一次接手这个仓库、要改一个文档或一条命令的工程师”。

## 硬约束
- 只读：不改文件、不装依赖、不 git add/commit/push。
- 证据：每个问题给 `file:line`；没有证据的标“推断”。
- 不把 `archive/` 的历史材料算进“必须理解”的当前成本；它只影响检索噪声，单独说明。
- 中文；先结论后依据。

## 步骤
1. 按新人的真实路径读一遍：`AGENTS.md` → `README.md` → `DEPLOYMENT.md` → `RELEASING.md` → `CHANGELOG.md` → `skills/personal-dev-workflow/SKILL.md` → 需要改的脚本或命令。
2. 记录理解路径：先读什么、在哪卡住、必须跳读哪些文件、哪些概念要先解释、哪些说法互相冲突。
3. 找五类成本：
   - 命名：同名不同义、缩写、历史叫法；
   - 抽象：为不存在的复用引入的层；
   - 职责：一个文件/脚本承担多个互不相关的职责；
   - 上下文：不读三份以上文档就看不懂的规则；
   - 入口：不知道从哪开始、哪份是权威。
4. 每个问题给：认知成本（低/中/高）、证据、简化方案、风险。
5. 按“降低认知成本的收益 / 改动风险”排序。

## 输出
- 结论：一句话说最大认知成本在哪。
- 理解路径：新人会怎么走、在哪卡住。
- 问题表：五类，逐条带证据、成本、简化方案、风险。
- 优先建议：前 3 条，附验证方式。

## 停止条件
只报告，不改文档或代码。涉及 Skill 本体的改动，先说明必须上游先行。
