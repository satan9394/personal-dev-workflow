# 存量冗余审计

## 角色与目标
你负责在 live tree 里找“看起来有用、实际没有价值”的东西：无用测试、不必要的包装、死代码、重复抽象、过期文档与注释。只报告，不删除。不要把 `archive/` 当成清理对象。

## 输入
`$ARGUMENTS` = 想重点审计的目录或主题。若为空，默认 `skills/personal-dev-workflow/`、`scripts/`、`.opencode/` 与根文档。

## 硬约束
- 只读：不改文件、不装依赖、不跑会写盘的命令、不 git add/commit/push。
- 读完整文件，不用 grep 结果代替调用链；必须追踪真实引用。
- `archive/` 是刻意保留的历史：只检查它是否被 live tree 误引用，不提议删除。
- Skill 本体的删除/合并必须先上游；本仓库只报告。
- 中文；先结论后依据。

## 步骤
1. 列出 live tree 的文件与入口，标出哪些是运行时代码、哪些是文档、哪些是开发工具。
2. 完整读一遍候选文件，追踪调用路径：谁引用它、它引用谁、删掉会怎样。
3. 分类：
   - 无用测试：永远通过、测不到真实行为、只测 mock；
   - 不必要包装：单次调用、无抽象收益、只为转发参数；
   - 死代码/死分支：没有入口、被开关永久关闭；
   - 重复抽象：两份做同一件事的脚本/文档/规则；
   - 过期文档/注释：描述的路径、数量、版本、行为已变；
   - 未使用依赖/脚本：`package.json` 或 CI 里已无引用。
4. 每个候选给：证据 `file:line`、真实调用路径、删除/合并风险、建议（保留/合并/改写/删除）。
5. 按“收益 / 风险”排序，先给低风险高收益。

## 输出
- 结论：一句话说冗余最集中的地方。
- 候选表：分类、证据、调用路径、风险、建议。
- 前 3 条：为什么值得先做、怎么验证。
- 明确保留：`archive/`、历史 tag、刻意的 legacy。

## 停止条件
只报告，不删除、不合并。需要改 Skill 本体时，先走上游。
