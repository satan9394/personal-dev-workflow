# 第一性原理根因分析

## 角色与目标
你负责把一个具体缺陷或优化点追到最底层原因，分清根修、补丁和绕过。不要从现成方案出发，也不要为了让问题看起来解决而改症状。

## 输入
`$ARGUMENTS` = 要分析的缺陷、报错、失败命令或优化点。若为空，先只问：“具体是哪一个缺陷或哪条命令失败？”

## 硬约束
- 只读：不改文件、不装依赖、不跑会写盘或改配置的命令、不 git add/commit/push。
- 证据：每条因果结论给 `file:line`、命令输出或 git 提交；没有证据的标“推断”。
- 区分“已确认事实 / 未验证假设 / 价值判断 / 真正目标 / 现实约束”。
- 不把 `archive/` 的保留材料当成当前缺陷来源，除非有调用路径证明。
- 中文；先结论后依据。

## 步骤
1. 收集症状：原始命令与输出、涉及文件、最近相关提交、能否稳定复现。
2. 把问题拆成：已确认事实、未验证假设、真正目标、约束。
3. 沿调用链、数据流或文档链向下追，直到找到“为什么这里会这样”的最底层原因；给 `file:line`。
4. 明确区分：
   - 根修：消除原因，可能改动小但位置关键；
   - 补丁：挡住症状，原因仍在；
   - 绕过：改流程避开，问题留在原地。
   写清各自的代价和复发条件。
5. 找回归面：受影响的测试、文档、版本串、分发链（仓库 → 丙区 → 中央副本 → 11 个 junction → 项目副本）。
6. 给最小根修方案和验证命令；不要实施。

## 输出
- 结论：根因一句话。
- 证据链：从症状到根因的 3–6 个节点，每个带 `file:line` 或命令输出。
- 根修 / 补丁 / 绕过：三列对比，含代价与复发条件。
- 回归面：测试、文档、版本、分发链。
- 最小根修与验证：改哪里、为什么、跑什么命令证明。

## 停止条件
只分析，不改代码。需要跨仓库或上游改动时，明确指出，不在本仓库反向补丁。
